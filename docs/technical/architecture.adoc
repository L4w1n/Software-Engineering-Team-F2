| Projektlaufzeit: Das Produkt wird in zwei Semestern umgesetzt, gegliedert in Sprints. Jeder Sprint endet mit einem Review.

== Architekturentscheidungen

_Architekturentscheidungen (Architecture Decision Records, ADRs) dokumentieren
wichtige technische Entscheidungen: Was wurde entschieden, warum, welche
Alternativen wurden verworfen, und welche Konsequenzen hat die Entscheidung._

_Jede Entscheidung, die schwer rückgängig zu machen ist oder das gesamte System
betrifft, sollte hier festgehalten werden. Kleine, lokale Implementierungsdetails
gehören nicht hierher._

NOTE: ADRs werden nicht gelöscht oder überschrieben — sie werden als
„ersetzt durch ADR-XXX" markiert. So bleibt die Entscheidungshistorie nachvollziehbar.

=== ADR-002 Wahl der grundlegenden Systemarchitektur

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| 28.05.2026

| *Kontext*
| Wir entwickeln eine Webanwendung, die eine klare Trennung zwischen Benutzeroberfläche, Fachlogik und Datenhaltung benötigt. Das Team arbeitet mit JavaScript im Frontend und Backend.Die Anwendung soll wartbar, testbar und innerhalb des Projektrahmens realistisch umsetzbar sein.

| *Entscheidung*
| Wir verwenden React/Vite im Frontend, Node.js/NestJS im Backend und Supabase PostgreSQL für die Datenhaltung. Frontend und Backend kommunizieren über eine REST-API mit JSON.

| *Alternativen*
| Supabase only ohne eigenes Backend; Spring Boot als Backend; klassische serverseitige Webanwendung ohne getrenntes Frontend.

| *Konsequenzen*
| Die Architektur ist klar getrennt und unterstützt eine wartbare Entwicklung. Durch JavaScript im Frontend und Backend entsteht ein einheitlicher Technologie-Stack. Frontend, Backend und Datenbank müssen jedoch getrennt entwickelt, integriert und getestet werden.
|===

=== ADR-003: Verwendung von React, JavaScript und Vite im Frontend

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| 28.05.2026

| *Kontext*
| Die Anwendung benötigt eine moderne und interaktive Benutzeroberfläche. Das Team hat erste Erfahrungen mit JavaScript und React. Die Anwendung soll für mobile Geräte geeignet sein und perspektivisch als PWA funktionieren.

| *Entscheidung*
| Wir verwenden React mit JavaScript und Vite für das Frontend.

| *Alternativen*
| Vue.js/Nuxt.js; React Native; Thymeleaf mit Spring Boot; serverseitiges Rendering mit Templates.

| *Konsequenzen*
| React ermöglicht komponentenbasierte Entwicklung der Benutzeroberfläche. Vite vereinfacht Entwicklung und Build-Prozess. Das Risiko ist, dass Fachlogik versehentlich in UI-Komponenten landen. Deshalb müssen Komponenten, Services und API-Zugriffe getrennt werden.
|===

=== ADR-004: Verwendung von Node.js und NestJS als Backend

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| 28.05.2026

| *Kontext*
| Die Anwendung benötigt eine zentrale Backend-Schicht für Fachlogik, Validierung und REST-Schnittstellen. Das Team verwendet bereits JavaScript im Frontend. Ein JavaScript-basiertes Backend reduziert den Technologiewechsel zwischen Frontend und Backend und erleichtert die Zusammenarbeit.

| *Entscheidung*
| Wir verwenden Node.js mit NestJS als Backend. Die Fachlogik wird in Services umgesetzt. Controller stellen REST-Endpunkte für das Frontend bereit.

| *Alternativen*
| Spring Boot als Backend; Supabase ohne eigenes Backend; Node.js mit Express.

| *Konsequenzen*
| NestJS bietet eine klare Projektstruktur mit Controllern, Services und Modulen. Dadurch wird die Trennung von Verantwortlichkeiten unterstützt. Der Nachteil ist ein höherer Einstieg als bei Express, insbesondere durch die stärkeren Framework-Konventionen.
|===

=== ADR-005: Verwendung des Supabase Clients für den Datenzugriff

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| 28.05.2026

| *Kontext*
| Das Backend muss auf die Supabase PostgreSQL gespeicherten Daten zugreifen. Dafür wird eine einfache und projektgeeignete Zugriffsschicht benötigt.

| *Entscheidung*
| Wir verwenden den Supabase Client für den Datenzugriff aus dem Node.js/NestJS-Backend.

| *Alternativen*
| Prisma; node-postgres; direkter Datenbankzugriff aus dem Frontend.

| *Konsequenzen*
| Der Supabase Client passt direkt zur gewählten Datenbankplattform und reduziert den Einrichtungsaufwand. Der Nachteil ist eine stärkere Bindung an Supabase-spezifische Schnittstellen. Bei wachsender Komplexität kann später ein strukturierter Zugriff über Prisma geprüft werden.
|===

=== ADR-006: Verwendung von Supabase PostgreSQL als Datenbank

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| 28.05.2026

| *Kontext*
| Die Anwendung benötigt eine relationale Datenbank für strukturierte Daten, zum Beispiel für Nutzerprofile, Einträge, Aufgaben, Statuswerte oder Reflexionen. Relationale Daten passen gut zu den erwarteten Datenstrukturen.

| *Entscheidung*
| Wir verwenden Supabase PostgreSQL als Datenbank.

| *Alternativen*
| Lokale PostgreSQL-Datenbank; Firebase; SQLite; MySQL

| *Konsequenzen*
| PostgreSQL passt gut zu relationalen Daten. Supabase reduziert den Aufwand für Einrichtung und Betrieb der Datenbank. Das Risiko ist die Abhängigkeit von Supabase als externen Dienst. Datenmodell, Rechte und Backups müssen bewusst geplant werden.
|===

=== ADR-007: Verwendung von Supabase Auth für Authentifizierung

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| 28.05.2026

| *Kontext*
| Die Anwendung benötigt Registrierung, Login und Sitzungsverwaltung. Authentifizierung ist sicherheitskritisch und sollte nicht unnötig selbst implementiert werden.

| *Entscheidung*
| Wir verwenden Supabase Auth für Registrierung, Login und Sitzungsverwaltung.

|===

=== ADR-008: Kommunikation über REST API mit JSON

[cols="1,3"]
|===
| *Status*
| Akzeptiert

| *Datum*
| 28.05.2026

| *Kontext*
| Frontend und Backend werden getrennt entwickelt. Deshalb wird eine klar definierte Schnittstelle benötigt, über die Daten zwischen React/Vite und dem NestJS-Backend ausgetauscht werden.

| *Entscheidung*
| Die Kommunikation zwischen Frontend und Backend erfolgt über eine REST API mit JSON.

| *Alternativen*

=== ADR-010: Automatisierte Qualitätssicherung mit GitHub Actions, Jest/Vitest und Supertest

[cols="1,3"]
|===
| *Status*
| Vorgeschlagen

| *Datum*
| 28.05.2026

| *Kontext*
| Frontend und Backend sollen nicht nur manuell geprüft werden. Fehler sollen früh erkannt werden, bevor Änderungen in den Hauptstand übernommen werden. Dafür werden automatisierte Tests und ein automatisierter Prüfprozess benötigt.

| *Entscheidung*
| Wir verwenden GitHub Actions für automatisierte Builds und Tests. Frontend-Komponenten werden mit Jest oder Vitest und React Testing Library getestet. Backend- und API-Funktionen werden mit Jest oder Vitest und Supertest getestet.

| *Alternativen*
| Nur manuelle Tests; lokale Tests ohne CI/CD; andere CI/CD-Plattformen wie GitLab CI.

| *Konsequenzen*
| Änderungen können automatisch geprüft werden. Die Codequalität und Stabilität der Anwendung steigen. Der Nachteil ist zusätzlicher Einrichtungsaufwand für Testskripte, Workflows und Testdaten. Außerdem müssen fehlgeschlagene Tests im Team konsequent behoben werden.
|===

=== ADR-011: Deployment- und Hostingstrategie für Frontend und Backend

[cols="1,3"]
|===
| *Status*
| Vorgeschlagen

| *Datum*
| 28.05.2026

| *Kontext*
| Die Anwendung soll nicht nur lokal laufen, sondern auch als nutzbares Produktinkrement bereitgestellt werden. Frontend und Backend werden getrennt entwickelt und benötigen daher passende Hosting-Optionen.

| *Entscheidung*
| Das Frontend wird über Vercel oder Netlify bereitgestellt. Das Node.js/NestJS-Backend wird über Render, Railway oder Fly.io bereitgestellt.

| *Alternativen*
| Lokale Ausführung ohne Deployment, eigener Server, Hochschulserver, vollständiges Deployment über eine einzige Plattform.

| *Konsequenzen*
| Frontend und Backend können unabhängig bereitgestellt werden. Vercel und Netlify sind gut für React/Vite-Projekte geeignet. Render, Railway und Fly.io eignen sich für Webservices und Docker-basierte Deployments. Der Nachteil ist zusätzlicher Konfigurationsaufwand für Umgebungsvariablen, Authentifizierung, Datenbankzugriff und Deployment-Pipeline.
|===
