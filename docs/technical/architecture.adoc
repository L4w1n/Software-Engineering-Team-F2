== Architekturentscheidungen

_Architekturentscheidungen (Architecture Decision Records, ADRs) dokumentieren
wichtige technische Entscheidungen: Was wurde entschieden, warum, welche
Alternativen wurden verworfen, und welche Konsequenzen hat die Entscheidung._

_Jede Entscheidung, die schwer rückgängig zu machen ist oder das gesamte System
betrifft, sollte hier festgehalten werden. Kleine, lokale Implementierungsdetails
gehören nicht hierher._

NOTE: ADRs werden nicht gelöscht oder überschrieben — sie werden als
„ersetzt durch ADR-XXX" markiert. So bleibt die Entscheidungshistorie nachvollziehbar.

=== ADR-002 Wahl der grundlegenden Systemarchitektur

[cols="1,3"]
|===
| *Status*
| Vorgeschlagen

| *Datum*
| 28.05.2026

| *Kontext*
| Wir entwickeln eine Webanwendung, die eine klare Trennung zwischen Benutzeroberfläche, Fachlogik und Datenhaltung benötigt. Das Team arbeitet mit JavaScript im Frontend und Backend.Die Anwendung soll wartbar, testbar und innerhalb des Projektrahmens realistisch umsetzbar sein.

| *Entscheidung*
| Wir verwenden React/Vite im Frontend, Node.js/Express im Backend und Supabase PostgreSQL für die Datenhaltung. Frontend und Backend kommunizieren über eine REST API mit JSON.

| *Alternativen*
| Supabase only ohne eigenes Backend; Spring Boot als Backend; klassische serverseitige Webanwendung ohne getrenntes Frontend.

| *Konsequenzen*
| Die Architektur ist sauber trennbar und gut dokumentierbar. Durch JavaScript in Frontend und backend entsteht ein einheitlicher Stack. Der Nachteil ist, dass Frontend, Backend und Datenbank separat entwickelt, integriert und getestet werden müssen.
|===

=== ADR-003: Verwendung von React, JavaScript und Vite im Frontend

[cols="1,3"]
|===
| *Status*
| Vorgeschlagen

| *Datum*
| 28.05.2026

| *Kontext*
| Die Anwendung benötigt eine moderne und interaktive Benutzeroberfläche. Das Team hat erste Erfahrungen mit JavaScript und React. Die Anwendung soll für mobile Geräte geeignet sein und perspektivisch als PWA funktionieren.

| *Entscheidung*
| Wir verwenden React mit JavaScript und Vite für das Frontend.

| *Alternativen*
| Vue.js/Nuxt.js; React Native; Thymeleaf mit Spring Boot; serverseitiges Rendering mit Templates.

| *Konsequenzen*
| React ermöglicht komponentenbasierte Entwicklung der Benutzeroberfläche. Vite vereinfacht Entwicklung und Build-Prozess. Das Risiko ist, dass Fachlogik versehentlich in UI-Komponenten landen. Deshalb müssen Komponenten, Services und API-Zugriffe getrennt werden.
|===

=== ADR-004: Verwendung von Node.js und Express als Backend

[cols="1,3"]
|===
| *Status*
| Vorgeschlagen

| *Datum*
| 28.05.2026

| *Kontext*
| Die Anwendung braucht eine zentrale Backend-Schicht für Fachlogik, Validierung und Schnittstellen. Das Team verwendet bereits JavaScript im Frontend. Ein JavaScript-basiertes Backend reduziert den Technologiewechsel zwischen Frontend und Backend.

| *Entscheidung*
| Wir verwenden Node.js mit Express als Backend. Die Fachlogik wird in Services umgesetzt. Express-Routen stellen REST-Endpunkte für das Frontend bereit.

| *Alternativen*
| Spring Boot als Backend; Supabase only ohne eigenes Backend; Node.js mit NestJS.

| *Konsequenzen*
| Node.js und Express ermöglichen ein leichtgewichtetes Backend und einen einheitlichen JavaScript-Stack. Der Einstieg ist einfacher als bei einem umfangreicheren Backend-Framework. Der Nachteil ist, dass Architektur, Strukturierung, Validierung und Fehlerbehandlung stärker selbst organisiert werden müssen.
|===

=== ADR-005: Verwendung des Supabase Clients für den Datenzugriff

[cols="1,3"]
|===
| *Status*
| Vorgeschlagen

| *Datum*
| 28.05.2026

| *Kontext*
| Das Backend muss auf die Supabase PostgreSQL gespeicherten Daten zugreifen. Dafür wird eine einfache und projektgeeignete Zugriffsschicht benötigt.

| *Entscheidung*

=== ADR-006: Verwendung von Supabase PostgreSQL als Datenbank

[cols="1,3"]
|===
| *Status*
| Vorgeschlagen

| *Datum*
| 28.05.2026

| *Kontext*
| Die Anwendung benötigt eine relationale Datenbank für strukturierte Daten, zum Beispiel für Nutzerprofile, Einträge, Aufgaben, Statuswerte oder Reflexionen. Relationale Daten passen gut zu den erwarteten Datenstrukturen.

[cols="1,3"]
|===

| Vorgeschlagen

| *Datum*
| 28.05.2026

=== ADR-008: Kommunikation über REST API mit JSON

[cols="1,3"]
|===
| *Status*
| Vorgeschlagen

| *Datum*
| 28.05.2026

=== ADR-010: Automatisierte Qualitätssicherung mit GitHub Actions, Jest/Vitest und Supertest

[cols="1,3"]
|===
| *Status*
| Vorgeschlagen

| *Datum*
| 28.05.2026

| *Kontext*
| Frontend und Backend sollen nicht nur manuell geprüft werden. Fehler sollen früh erkannt werden, bevor Änderungen in den Hauptstand übernommen werden. Dafür werden automatisierte Tests und ein automatisierter Prüfprozess benötigt.

| *Entscheidung*

=== ADR-011: Deployment- und Hostingstrategie für Frontend und Backend

[cols="1,3"]
|===
| *Status*
| Vorgeschlagen

| *Datum*
| 28.05.2026

| *Kontext*
| Die Anwendung soll nicht nur lokal laufen, sondern auch als nutzbares Produktinkrement bereitgestellt werden. Frontend und Backend werden getrennt entwickelt und benötigen daher passende Hosting-Optionen.

| Das Frontend wird über Vercel oder Netlify bereitgestellt. Das Node.js/Express-Backend wird über Render, Railway oder Fly.io bereitgestellt. Die konkrete Plattform wird nach einem technischen Durchstich final festgelegt.

Der Nachteil ist zusätzlicher Konfigurationsaufwand für Umgebungsvariablen, CORS, Backend-URL, Datenbankzugang und Deployment-Pipeline.

== Risiken & technische Schulden

_Dieser Abschnitt dokumentiert bekannte technische Risiken und bewusst eingegangene
technische Kompromisse (Technical Debt). Transparenz hier verhindert, dass diese

=== Technische Risiken

[cols="2,1,2,2", options="header"]
|===
| Risiko | Auswirkung | Wahrscheinlichkeit | Maßnahme

| Integration zwischen React/Vite-Frontend und Node.js/Express-Backend funktioniert nicht reibungslos
| Hoch
| Mittel
| Früh einen technischen Durchstich bauen; einfache React-Seite ruft einen Express-REST-Endpunkt auf und zeigt Daten an.

| Authentifizierung mit Supabase Auth und Express-Backend ist unklar
