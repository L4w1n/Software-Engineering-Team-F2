== Wichtige Interaktionsflüsse

Sequenzdiagramme zeigen, wie Komponenten bei typischen Abläufen zusammenarbeiten.
Dokumentiert werden hier nur die wichtigsten und komplexesten Flüsse —
nicht jede einfache CRUD-Operation.

=== Check-In erfassen

Dieser Ablauf zeigt die Erfassung eines täglichen Check-Ins durch einen Studierenden.
Die eingegebenen Werte werden validiert und gespeichert. Die gespeicherten Daten bilden die Grundlage für spätere Analysen, Warnungen und Empfehlungen.

[plantuml, sequence-checkin, svg]
....
@startuml
skinparam monochrome true
skinparam defaultFontSize 12

actor "Studierender" as user
participant "Check-In UI" as ui
participant "REST Controller" as ctrl
participant "Check-In Service" as service
participant "Supabase Client" as client

user -> ui : Check-In ausfüllen\n(Energie, Stress,\nStimmung, Reflexion)
ui -> ctrl : POST /api/v1/checkins
ctrl -> ctrl : Eingaben validieren
ctrl -> service : createCheckIn()
service -> client : speichern()
client --> service : gespeicherter Check-In
service --> ctrl : Erfolg
ctrl --> ui : 201 Created
ui --> user : Bestätigung anzeigen

@enduml
....

=== Datenbankmigrationen

Schemaänderungen werden nicht manuell durchgeführt, sondern über versionierte
Migrationsskripte verwaltet. Dadurch bleibt die Datenbankstruktur nachvollziehbar,
reproduzierbar und zwischen Entwicklungs- und Produktivumgebungen konsistent.

[cols="1,3", options="header"]
|===
| Aspekt | Beschreibung

| Werkzeug
| Supabase CLI Migrations

| Speicherort
| `supabase/migrations/`

| Namenskonvention
| Zeitstempelbasierte Benennung, z. B. `20250610120000_initial_schema.sql`

| Regel
| Bereits ausgeführte Migrationen werden nicht verändert. Änderungen am Schema erfolgen ausschließlich über neue Migrationen.

| Deployment
| Migrationen werden über die Supabase CLI auf die Zielumgebung angewendet.
|===

== Eingesetzte Muster & Konventionen

_Dieser Abschnitt dokumentiert übergreifende Designmuster und Konventionen, die im
gesamten Codebase gelten. Das verhindert, dass verschiedene Teammitglieder dasselbe
Problem auf unterschiedliche Weise lösen._

=== Designmuster

[cols="1,2,2", options="header"]
|===
| Muster | Wo eingesetzt | Begründung

| Service Layer
| Backend (Check-In Service, Task Service, Analysis Service, Auth Service)
| Trennung von HTTP-Verarbeitung und Geschäftslogik; Controller bleiben schlank und delegieren fachliche Aufgaben an Services

| Component-Based Architecture
| Frontend (React)
| Benutzeroberfläche wird aus wiederverwendbaren Komponenten aufgebaut; verbessert Wartbarkeit und Wiederverwendbarkeit

| Separation of Concerns
| Gesamte Anwendung
| Präsentation, Geschäftslogik und Datenzugriff werden in getrennten Schichten umgesetzt; reduziert Kopplung und erleichtert Erweiterungen

| RESTful API Design
| Kommunikation zwischen Frontend und Backend
| Klare Ressourcenorientierung und standardisierte Kommunikation über HTTP und JSON
|===

=== Fehlerbehandlung

[cols="1,3", options="header"]
|===
| Aspekt | Konvention

| Validierungsfehler
| Ungültige oder unvollständige Eingaben werden mit HTTP Statuscode `400 Bad Request` beantwortet

| Nicht gefundene Ressourcen
| Nicht vorhandene Check-Ins oder Aufgaben werden mit `404 Not Found` beantwortet

| Authentifizierungsfehler
| Fehlende oder ungültige Anmeldedaten werden mit `401 Unauthorized` beantwortet

| Serverfehler
| Unerwartete Fehler werden mit `500 Internal Server Error` beantwortet

| Fehlermeldungen
| Fehler werden als strukturierte JSON-Antworten zurückgegeben

| Logging
| Fehler werden serverseitig protokolliert; sensible Nutzerdaten werden nicht in Logdateien gespeichert
|===

=== API-Konventionen

[cols="1,3", options="header"]
|===
| Aspekt | Konvention

| URL-Struktur
| Ressourcenorientierte Endpunkte im Plural, z. B. `/api/v1/checkins`, `/api/v1/tasks`, `/api/v1/analysis`

| HTTP-Methoden
| GET = lesen; POST = erstellen; PUT = vollständiges Aktualisieren; PATCH = teilweises Aktualisieren; DELETE = löschen

| Antwortformat
| JSON für alle Anfragen und Antworten

| Datumsformat
| ISO-8601 Format, z. B. `2025-06-15T14:30:00Z`

| HTTP-Statuscodes
| 200 für erfolgreiche Anfragen; 201 für erfolgreich erstellte Ressourcen; 400 für fehlerhafte Eingaben; 401 für Authentifizierungsfehler; 404 für nicht gefundene Ressourcen; 500 für unerwartete Serverfehler

| Authentifizierung
| Authentifizierte Anfragen verwenden die von Supabase Auth bereitgestellten Tokens

| Versionierung
| Versionierung über URL-Präfix (`/api/v1/`); neue Hauptversionen nur bei inkompatiblen Änderungen
|===
